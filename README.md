# CloudRepairs — сайт и админ-панель

Сайт CloudRepairs («Облачные ремонты») с собственной системой управления содержимым.

- **Публичный сайт** — React + TypeScript, серверный рендеринг (каждая страница приходит готовым HTML для SEO).
- **Админ-панель** — `/admin`: новости, партнёры, кейсы, продукты, тексты страниц, медиафайлы, контакты.
- **Сервер** — Node.js + Express, база данных SQLite (один файл), миграции, REST API.

Админка и сайт работают с одной базой: изменение, сохранённое в админке, видно на сайте сразу,
без пересборки и без правки кода.

Происхождение текстов и что не перенесено со старого сайта — в [AUDIT.md](AUDIT.md).

## Быстрый старт (разработка)

Нужен **Node.js 20.11+** (рекомендуется 22 LTS).

```bash
npm install
npm run admin:create -- --email you@example.ru --name "Имя"   # пароль спросит в терминале
npm run dev                                                    # http://localhost:3000, админка: /admin
```

При первом запуске сервер сам создаёт базу `data/cloudrepairs.db`, применяет миграции и заполняет
её текущим содержимым сайта (тексты страниц, продукты, кейсы, партнёры, контакты).
Папка `data/` в git не попадает.

| Команда | Что делает |
|---|---|
| `npm run dev` | Сервер разработки с горячей перезагрузкой (сайт + админка + API) |
| `npm run build` | Проверка типов и production-сборка в `dist/` |
| `npm start` | Запуск собранного сайта (`NODE_ENV=production`) |
| `npm test` | Интеграционные тесты API и сайта (32 проверки) |
| `npm run admin:create` / `admin:create:prod` | Создать администратора или сменить пароль |
| `npm run backup` / `backup:prod` | Резервная копия базы и изображений |

## Создание администратора

Пароля «по умолчанию» нет — ни в коде, ни в базе. Первый (и любой следующий) администратор
создаётся командой на сервере, доступ к которой есть только у владельца сервера:

```bash
# разработка
npm run admin:create -- --email owner@cloudrepairs.ru --name "Владимир"

# production (после npm run build), с теми же переменными окружения, что и у сайта
set -a; . /etc/cloudrepairs.env; set +a
npm run admin:create:prod -- --email owner@cloudrepairs.ru --name "Владимир"
```

- Пароль вводится скрытно в терминале (дважды). Для автоматизации можно передать его через переменную
  окружения `ADMIN_PASSWORD` — тогда не сохраняйте его в истории командной строки и файлах.
- Требования к паролю: не короче 10 символов, буквы и цифры.
- **Забыли пароль** — та же команда с `--reset`: пароль заменяется, все сеансы этого администратора завершаются.
  ```bash
  npm run admin:create:prod -- --email owner@cloudrepairs.ru --reset
  ```
- Пароль можно сменить и в админке: «Настройки → Смена пароля» (другие сеансы при этом завершаются).

## Работа в админ-панели

Адрес: `https://ваш-домен/admin`. Ссылок на админку на сайте нет — адрес открывается вручную.

| Раздел | Возможности | Где видно на сайте |
|---|---|---|
| Главная панель | Число опубликованных новостей, партнёров, кейсов, продуктов; последние изменения | — |
| Новости | Создание, редактирование, черновики, публикация/снятие, отложенная дата, удаление; поиск по заголовку, фильтр по статусу, сортировка по дате; обложка, адрес (slug), краткое описание, текст с заголовками, списками, ссылками и изображениями, SEO | `/news/`, `/news/<slug>/`, блок «Новости» на главной (появляется, когда есть хотя бы одна новость), пункт меню «Новости» |
| Партнёры | Добавление, логотип, название, сайт, описание, показать/скрыть, порядок, удаление | Блок «Партнёры» на главной и на странице «О нас» |
| Кейсы | Создание, публикация, порядок, обложка и галерея, клиент, партнёр, краткое и полное описание, связанные ссылки, SEO | Блок «Кейсы» на главной; при заполненном полном описании — страница `/cases/<slug>/` |
| Продукты | Создание, публикация, порядок, изображение, описание, подробный текст, ссылка карточки, SEO | Блок «Продукты и услуги» на главной; страница `/products/<slug>/`, если есть подробный текст и не задана ссылка |
| Страница «О нас» | Тексты разделов, изображения и подписи, кнопки и их ссылки, порядок блоков, SEO | `/about/` |
| Тексты страниц | То же для главной, «Обучения» и страницы продукта («внутреннее обучение») | `/`, `/obuchen/`, `/vnutyankaya-training/` |
| Медиафайлы | Загрузка (в т. ч. перетаскиванием), поиск, описание (alt), замена файла с сохранением адреса, удаление (только если файл нигде не используется — иначе показывается, где он используется) | везде, где выбрано изображение |
| Настройки | E-mail для заявок, телефон, Телеграм, тексты кнопок в шапке и подвале, копирайт; смена пароля | Шапка и подвал всех страниц |
| Выйти | Завершение сеанса на сервере | — |

Как устроено редактирование страниц: у каждой страницы есть схема (`shared/schema.ts`) —
какие тексты, изображения, ссылки и списки можно менять и какие блоки можно переставлять.
Форма строится по схеме, сервер проверяет данные по ней же, поэтому сломать вёрстку через админку нельзя:
первый экран и завершающий блок всегда на своих местах, переставляются только разрешённые блоки.

## Переменные окружения

Полный пример с комментариями — [.env.example](.env.example).

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `NODE_ENV` | — | `production` на сервере (включает CSP, Secure-cookie, отдачу собранных файлов) |
| `HOST` / `PORT` | `0.0.0.0` / `3000` | Где слушает Node.js. За nginx — `127.0.0.1` |
| `PUBLIC_URL` | `https://cloudrepairs.ru` | Адрес сайта для sitemap, canonical, Open Graph |
| `DATA_DIR` | `./data` | База SQLite и папка `uploads/` с изображениями |
| `BACKUP_DIR` | `./backups` | Куда складываются резервные копии |
| `TRUST_PROXY` | `false` | `true` за nginx — чтобы ограничение попыток входа учитывало реальный IP |
| `COOKIE_SECURE` | `true` в production | Cookie сессии только по HTTPS. `false` — только для локальной проверки по http |
| `SESSION_TTL_HOURS` | `12` | Максимальное время жизни сессии |
| `SESSION_IDLE_MINUTES` | `120` | Выход после бездействия |
| `LOGIN_MAX_ATTEMPTS` | `5` | Неудачных попыток входа до блокировки (для одного IP порог в 4 раза выше) |
| `LOGIN_WINDOW_MINUTES` | `15` | Окно подсчёта попыток и длительность блокировки |
| `MAX_UPLOAD_MB` | `10` | Максимальный размер загружаемого файла |
| `ADMIN_PASSWORD` | — | Только для команды `admin:create` при запуске без терминала |

Сервер сам `.env` не читает: переменные задаются в systemd (`EnvironmentFile`), в панели хостинга
или при запуске (`node --env-file=.env dist/server/index.js`).

## Развёртывание на сервере

Пример для Ubuntu + nginx + systemd. Нужен постоянный диск (не «эфемерный» контейнер): там хранятся база и изображения.

```bash
# 1. Код и сборка
sudo useradd --system --home /opt/cloudrepairs cloudrepairs
sudo git clone <репозиторий> /opt/cloudrepairs && cd /opt/cloudrepairs
npm ci
npm run build
npm prune --omit=dev        # необязательно: убрать инструменты сборки

# 2. Каталоги данных и настройки
sudo mkdir -p /var/lib/cloudrepairs /var/backups/cloudrepairs
sudo chown cloudrepairs: /var/lib/cloudrepairs /var/backups/cloudrepairs
sudo cp .env.example /etc/cloudrepairs.env && sudo nano /etc/cloudrepairs.env
sudo chmod 600 /etc/cloudrepairs.env

# 3. Администратор
sudo -u cloudrepairs bash -c 'set -a; . /etc/cloudrepairs.env; set +a; cd /opt/cloudrepairs; npm run admin:create:prod -- --email owner@cloudrepairs.ru'
```

`/etc/systemd/system/cloudrepairs.service`:

```ini
[Unit]
Description=CloudRepairs site
After=network.target

[Service]
User=cloudrepairs
WorkingDirectory=/opt/cloudrepairs
EnvironmentFile=/etc/cloudrepairs.env
ExecStart=/usr/bin/node dist/server/index.js
Restart=on-failure
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/var/lib/cloudrepairs /var/backups/cloudrepairs

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now cloudrepairs
```

nginx (HTTPS обязателен — без него cookie сессии не будет работать в production):

```nginx
server {
    listen 443 ssl http2;
    server_name cloudrepairs.ru;
    # ssl_certificate / ssl_certificate_key — например, от certbot

    client_max_body_size 12m;          # чуть больше MAX_UPLOAD_MB

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    # Дополнительно можно ограничить /admin по IP:
    # location /admin { allow 1.2.3.4; deny all; proxy_pass http://127.0.0.1:3000; ... }
}
server { listen 80; server_name cloudrepairs.ru; return 301 https://$host$request_uri; }
```

Если на этом же домене работает сама система CloudRepairs (например, `/Account/Login`), направьте её
адреса на неё отдельными `location` до `location /`.

**Обновление сайта:** `git pull && npm ci && npm run build && sudo systemctl restart cloudrepairs`.
Миграции базы применяются автоматически при запуске; данные и изображения не затрагиваются.

## База данных и миграции

- SQLite, файл `$DATA_DIR/cloudrepairs.db` (режим WAL, внешние ключи включены). Изображения — `$DATA_DIR/uploads/`.
- Миграции — SQL-файлы в `server/db/migrations/` (`001_init.sql`, …). При запуске сервер применяет
  ещё не применённые по порядку имени, каждую в транзакции, и записывает в таблицу `schema_migrations`.
- Новая миграция: создайте `server/db/migrations/002_описание.sql`, выполните `npm run build` и перезапустите сервер.
  Уже применённые файлы не изменяйте.
- Начальное наполнение (`server/db/seed.ts`) выполняется один раз — на пустой базе; повторно контент не перезаписывает.
- Таблицы: `admins`, `sessions`, `login_attempts`, `media`, `news`, `partners`, `cases`, `case_images`,
  `products`, `pages`, `settings`, `schema_migrations`.

## Резервное копирование и восстановление

```bash
npm run backup:prod     # с переменными окружения сайта; можно при работающем сайте
```

Создаёт `$BACKUP_DIR/<дата-время>/` с согласованным снимком базы (`cloudrepairs.db`) и копией `uploads/`.
Пример ежедневного запуска (cron пользователя `cloudrepairs`), хранение 30 дней:

```cron
30 3 * * * set -a; . /etc/cloudrepairs.env; set +a; cd /opt/cloudrepairs && node dist/server/cli/backup.js && find /var/backups/cloudrepairs -mindepth 1 -maxdepth 1 -mtime +30 -exec rm -rf {} +
```

Храните копии и вне сервера (rsync/облачное хранилище).

**Восстановление:**

```bash
sudo systemctl stop cloudrepairs
cd /var/lib/cloudrepairs
rm -f cloudrepairs.db-wal cloudrepairs.db-shm
cp /var/backups/cloudrepairs/<копия>/cloudrepairs.db ./cloudrepairs.db
rm -rf uploads && cp -r /var/backups/cloudrepairs/<копия>/uploads ./uploads
chown -R cloudrepairs: /var/lib/cloudrepairs
sudo systemctl start cloudrepairs
```

## Безопасность

- **Пароли** — scrypt (N=2¹⁵, r=8, p=1, соль 16 байт, ключ 64 байта), сравнение за постоянное время.
  Для несуществующего e-mail тоже выполняется проверка хеша — по времени ответа нельзя узнать, есть ли такой логин.
- **Сессии** — случайный 256-битный токен в cookie `HttpOnly; Secure; SameSite=Strict` с префиксом `__Host-`;
  в базе хранится только SHA-256 токена. Ограничение по времени жизни и по бездействию; выход и смена
  пароля удаляют сессию на сервере.
- **Права проверяются на сервере**: все маршруты `/api/admin/*`, кроме входа, требуют действующей сессии (иначе 401).
  Интерфейс админки без сессии показывает только форму входа, но защита — именно на сервере.
- **CSRF** — у каждой сессии свой токен; любой изменяющий запрос должен передать его в заголовке `X-CSRF-Token`
  (иначе 403). Дополнительно проверяются `Origin`/`Sec-Fetch-Site` и действует `SameSite=Strict`.
- **Ограничение попыток входа** — счётчики в базе (переживают перезапуск) по e-mail и по IP; при превышении — 429 и `Retry-After`.
- **XSS** — React экранирует вывод; HTML из визуального редактора очищается на сервере по белому списку тегов
  (`sanitize-html`): удаляются скрипты, обработчики событий, `style`, `iframe`, ссылки `javascript:`;
  изображения в тексте — только из медиатеки. Content-Security-Policy с nonce: на страницах не выполняются чужие скрипты.
  Данные для гидратации встраиваются как JSON с экранированием `<`.
- **SQL-инъекции** — только параметризованные запросы (better-sqlite3), включая поиск (`LIKE` с экранированием).
- **Валидация** — все входные данные проверяются схемами zod на сервере (длины, форматы, ссылки, статусы, ссылки на медиафайлы);
  ошибки возвращаются с указанием поля.
- **Загрузка файлов** — только изображения JPG/PNG/WebP/GIF/AVIF; файл реально декодируется (подделка с
  расширением `.png` отклоняется), SVG и любые не-изображения запрещены, лимит размера, пересохранение в WebP
  (метаданные удаляются, размер до 2400 px), случайное имя (UUID), отдача с `nosniff`.
- **Прочее** — заголовки helmet (HSTS, `frame-ancestors 'none'`, `nosniff`, `Referrer-Policy`),
  `noindex` и `Disallow` для `/admin` и `/api/`, в клиентском коде нет паролей и ключей.

## API

Все ответы — JSON; ошибки — `{ "error": "...", "details": [{ "path", "message" }] }`.
Статусы: `200`, `201` (создано), `204` (удалено), `400` (ошибка данных), `401` (нет входа),
`403` (CSRF), `404`, `409` (файл используется / конфликт), `413`, `415` (не изображение), `429`.

| Метод и путь | Назначение |
|---|---|
| `GET /api/public/site` | Всё опубликованное содержимое сайта |
| `GET /api/public/news/:slug`, `/cases/:slug`, `/products/:slug` | Опубликованная запись |
| `POST /api/admin/auth/login`, `POST …/logout`, `GET …/session`, `POST …/password` | Вход, выход, проверка сессии, смена пароля |
| `GET /api/admin/stats` | Сводка для главной панели |
| `GET/POST /api/admin/news`, `GET/PUT/DELETE …/news/:id`, `PATCH …/news/:id/status` | Новости (`?q=`, `?status=`, `?sort=date_desc\|date_asc`) |
| `GET/POST /api/admin/partners`, `GET/PUT/DELETE …/:id`, `PATCH …/:id/visibility`, `POST …/reorder` | Партнёры |
| `GET/POST /api/admin/cases`, `GET/PUT/DELETE …/:id`, `PATCH …/:id/status`, `POST …/reorder` | Кейсы |
| `GET/POST /api/admin/products`, `GET/PUT/DELETE …/:id`, `PATCH …/:id/status`, `POST …/reorder` | Продукты |
| `GET /api/admin/pages`, `GET/PUT /api/admin/pages/:key` | Тексты страниц (`home`, `training`, `about`, `product`) |
| `GET/POST /api/admin/media`, `GET/PATCH/DELETE …/:id`, `PUT …/:id/file` | Медиафайлы (загрузка — `multipart/form-data`, поле `file`) |
| `GET/PUT /api/admin/settings` | Контакты и тексты шапки/подвала |

## Тесты

```bash
npm test
```

с проверкой публичных страниц, черновики и отложенную публикацию, очистку HTML от XSS, тексты и порядок блоков страниц,
отклонение опасных ссылок, загрузку/замену/удаление изображений, отказ для не-изображений,
сохранность данных и сессии после перезапуска.

## Что сделано и что не проверено

**Сделано и проверено** (автотесты `npm test` — 32 из 32, плюс сценарий в браузере Chromium на production-сборке — 32 из 32):

- Админка по `/admin`, без ссылок на сайте; «Войти» убрано из меню и подвала; `noindex`.
- Форма входа, сообщение о неверном пароле, сохранение сессии после обновления страницы, выход с завершением сессии на сервере.
- 401 для всех закрытых API без входа, 403 без CSRF-токена или с чужим `Origin`, 429 после серии неудачных входов.
- Новости: создание с заголовком H2, списком, ссылкой и обложкой из визуального редактора; публикация, появление на `/news/`,
  на главной и на своей странице; редактирование, SEO-поля, поиск, сортировка, снятие с публикации, удаление с подтверждением;
  черновик и отложенная дата не видны на сайте.
